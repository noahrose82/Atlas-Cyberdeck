# Atlas Cyberdeck — Pre-Launch Plan

## Phase Objective

Move Atlas Cyberdeck from a technically proven alpha with professional documentation into a campaign-ready product with an audience, a clear funding story, and repeatable demonstrations.

---

# Phase A — Campaign Foundation

**Status:** ACTIVE

Deliverables:

- campaign positioning;
- Kickstarter draft;
- founder story;
- reward model;
- risk section;
- funding-goal model;
- demo-video narrative;
- visual proof sequence.

Exit condition:

> A reviewer can understand what Atlas is, what already works, what remains to be built, and why funding is useful.

---

# Phase B — Public Landing Page

Deliverables:

- hero statement;
- real-device screenshots;
- email signup;
- "what works today" section;
- Linux runtime proof;
- safety/recovery story;
- founder attribution;
- public roadmap link;
- GitHub/GitLab links where appropriate;
- privacy-safe analytics only if needed.

Primary message:

> **A real Linux workstation in your pocket. No root required.**

Secondary message:

> **Ubuntu on Android — built as a product, not just a terminal.**

---

# Phase C — Demo Video

Target:

**90–150 seconds for the primary campaign cut.**

Required footage:

- physical phone in hand;
- Atlas boot;
- Dashboard;
- Linux Manager;
- `linux start`;
- `linux shell`;
- Ubuntu version;
- `uname -m`;
- Python;
- package workflow;
- Atlas Safe Mode;
- controlled recovery.

Rules:

- show the real build;
- minimize mockups;
- avoid excessive terminal scrolling;
- use readable close-ups;
- demonstrate before explaining;
- keep founder narration natural;
- no requirement for continuous on-camera appearance.

---

# Phase D — Audience Build

Before campaign launch:

- landing page live;
- mailing-list signup available;
- GitHub README polished;
- demo clip ready;
- short social assets ready;
- campaign preview link reviewed by trusted testers;
- early supporters identified;
- first-day communication plan prepared.

Key principle:

> Do not launch into an empty room.

---

# Phase E — Campaign Budget

Create a real budget before choosing a funding goal.

Budget categories:

| Category | Notes |
|---|---|
| Development reserve | Time required to complete public-release work |
| Test devices | Android ABI/vendor/OS diversity |
| Software/services | Hosting, signing, design, build infrastructure |
| Legal/accounting | Business, tax, licensing review |
| Campaign production | Video/audio/assets |
| Documentation/support | Public docs, issue workflow |
| Reward fulfillment | Digital/physical if applicable |
| Contingency | Unexpected engineering or fulfillment costs |
| Platform/payment fees | Model current Kickstarter + processor fees |

Do not announce a funding goal until this table contains defensible numbers.

---

# Phase F — Reward Validation

Recommended principle:

**Prefer digital rewards.**

Before finalizing any tier, answer:

1. What does the backer receive?
2. Can Atlas deliver it even if the schedule moves?
3. Does the reward create permanent support obligations?
4. Does the reward conflict with future Free / Pro boundaries?
5. Is fulfillment cost predictable?
6. Does it create tax/accounting complexity?
7. Is the wording a promise Atlas can actually keep?

Lifetime rewards require special caution.

---

# Phase G — Campaign Preview Review

Review the private campaign preview against:

- product accuracy;
- current screenshots;
- roadmap;
- reward promises;
- delivery dates;
- funding use;
- risks;
- grammar;
- mobile rendering;
- accessibility;
- links;
- founder identity;
- Android/Ubuntu trademark wording;
- license/open-source attributions where applicable.

Get outside eyes on the campaign before submission.

# First 48 Hours

Prepare before launch:

- launch email;
- short personal announcement;
- GitHub/README campaign notice;
- project screenshots;
- short Ubuntu demo;
- FAQ responses;
- technical explainer;
- founder update;
- thank-you message.

The goal is concentrated early momentum without pretending organic demand already exists.

---

# Campaign Principle

Atlas should sell **proof**, not hype.

The strongest argument is already available:

> The core Linux runtime is not a concept render. It runs today on real Android hardware.

Everything in the campaign should reinforce that fact.
